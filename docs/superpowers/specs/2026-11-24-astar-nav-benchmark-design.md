# 알바 길찾기 비교 — NavMesh vs 방 단위 A* (설계)

> 2026-11-24 · 사용자 요청 · 작업 번호 없음 (시험 · 측정용). 구현 계획은 이 문서 승인 뒤 `docs/superpowers/plans/`에 쓴다.

## 1. 목적 · 이유

- **질문**: 알바 100명일 때 지금 NavMesh와 맞춤 A* 중 어느 쪽이 CPU를 덜 쓰는가. Profiler 수치로 답한다.
- **왜**: 나중에 레일(컨베이어) · 오브젝트를 깔 때마다 맵 전체를 다시 굽지 않고 **그 방만** 다시 굽고 싶다. 목표는 CPU 사용량 최적화. 알바가 좀 멍청하게 움직여도 된다.
- **알파 대비**: 프로토타입은 버린다. A*는 알파로 그대로 옮길 수 있게 게임 코드와 떨어진 시스템으로 만든다.
- **지금 알고 있는 것** (CheckList 2026-11-23 프로파일, 알바 100명): NavMesh 비용은 프레임당 **0.35ms**, 느린 원인은 일감 찾기(`StaffWorker.Update` 30ms). 그래서 평소 CPU에서 아낄 수 있는 몫은 작고, 차이는 **해금 · 설치 순간의 굽기**에서 날 가능성이 크다. 이번 측정이 이것을 확인한다.

## 2. 목표 · 비목표 · 실패 조건

**목표**
1. 같은 조건에서 알바 100명 평소 CPU: NavMesh vs A*.
2. 길 1개 계산 비용: NavMesh vs 방 2층 A* vs 한 장 격자 A*.
3. 해금(방 열기) 굽기 비용: NavMesh 전체(지금) vs A* 전체 · 방별.
4. 레일 1개 · 10개 설치 비용: NavMesh(carving = 지금 선반 방식, 전체 굽기) vs A* 전체 · 방별 · 타일별.
5. A* 코어를 알파로 옮길 수 있는 모양(폴더 · 어셈블리 · 설정 에셋)으로.

**비목표**
- `StaffWorker`를 A*로 바꾸기 (측정 전용 알바로 비교 — 사용자 결정).
- 알바끼리 피하기, 가속, 예쁜 곡선 이동.
- 레일 기능 자체 (기획이 "컨베이어 벨트 — 논의 중"뿐). 레일은 **지나갈 수 없는 상자 장애물**로 흉내 낸다.
- 실기기 측정 (이번엔 에디터. 실기기 APK는 다음 단계).

**실패 조건** (돌아가도 실패로 본다)
- 비교가 불공평함: 두 방식의 알바 수 · 목적지 · 속도 · 화면에 그리는 것이 다르면 안 된다.
- A* 길이 막힌 칸(선반 · 레일)을 지나감.
- 한 장 격자 A*로는 길이 있는데 방 2층 A*가 못 찾음.
- 프로토타입 게임 동작이 바뀜 (씬 · `StaffWorker` · `Interactor`를 고치지 않는다).

## 3. 제약

- Unity 6000.3.26f1, 어셈블리 정의 없음(전부 Assembly-CSharp), 테스트 프레임워크 없음.
- 수치는 `Assets/Data`의 ScriptableObject에 둔다 (CheckList 5절).
- `TycoonTest.unity`는 누군가 저장 안 한 수정이 있다 → **씬 파일을 고치거나 저장하지 않는다.** 측정 도구는 Play 중에 코드로 붙인다.
- 같은 날 다른 계획이 `StaffWorker` · `Interactor`를 고친다 (`2026-11-24-interactor-tick.md`) → 두 파일은 건드리지 않는다.
- 지금 NavMesh: Site 루트 `NavMeshSurface`, 모듈 바닥 충돌체에만 굽기, 굽기 에이전트 반지름 **0.5** · 높이 2 · 복셀 0.167 · 타일 42.7m(256복셀). 알바 에이전트는 반지름 0.3 · 높이 1.2 · 속도 2.5 · 회피 끔. 선반 · 팔레트 랙은 Play 중 생기고 `NavMeshObstacle`(carve)로 구멍.

## 4. 접근 (고른 것: 1)

| | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **1. 방 단위 2층 (고름)** | 방마다 0.5m 격자. 방끼리 맞닿은 변에 문, 방 안 문↔문 거리 · 길을 미리 굽는다. 길 = 문 그래프 A* + 미리 구운 방 안 길 | 길 1개 비용이 맵 크기와 거의 무관 (알바 100명 평소 CPU, 알파의 큰 맵) | 방 하나 다시 굽기가 조금 무겁다, 코드가 가장 김 |
| 2. 맵 한 장 격자 | 0.5m 격자 한 장에서 매번 A* | 다시 굽기 = 칸만 다시 칠함 (가장 쌈), 코드 짧음 | 먼 길일수록 비쌈 → 알바가 많으면 평소 CPU 증가 |
| 3. 2m 타일 웨이포인트만 | 타일 중심만 길목 | 가장 쌈 | 선반(1.6m)보다 거칠어 선반을 뚫고 지나감 — 탈락 |

쿼드트리는 쓰지 않는다: 방 하나가 400칸이라 줄일 게 거의 없고 다시 굽기만 복잡해진다.
2는 1 안에서 방 안 길찾기 · 자기 검사용으로 같이 생기므로 **길 1개 비용 비교에는 넣는다.**

## 5. 설계

### 5.1 용어 · 크기

| 이름 | 크기 | 비고 |
|---|---|---|
| 방 | 모듈 칸 10m × 10m | 지금 모듈은 전부 1×1. `SiteGrid` 칸 (열, 행) |
| 타일 | 바닥 타일 2m × 2m | 방 하나 = 5 × 5 타일 (`ModuleFloor.tileSize`) |
| 격자 칸 | 0.5m × 0.5m `임시` | 방 = 20 × 20 칸, 타일 = 4 × 4 칸 |
| 문(게이트) | 변 하나의 이어진 열린 칸 묶음마다 가운데 한 쌍 | 양쪽 방에 하나씩 |

TycoonTest 8 × 8 = 방 64개, 격자 160 × 160 = 25,600칸.

### 5.2 코드 위치 (알파로 옮길 단위)

```
Assets/Scripts/Navigation/            ← APC.Navigation.asmdef (게임 코드를 모름, UnityEngine만)
  NavGrid.cs           격자 · 방 열림 · 막힌 칸 · 월드↔칸
  NavBox.cs            장애물 상자 (중심 · 반크기 · 회전) — 레일도 이것으로 등록
  RoomGates.cs         방 변의 문 찾기 · 문마다 방 안 거리 · 길 지도 굽기
  GridAStar.cs         사각형 범위 A* (방 하나 또는 맵 전체), 8방향, 모서리 자르기 금지
  RoomPathfinder.cs    방 2층 길찾기 + 직선 펴기 (시야 검사)
  NavCrowd.cs          알바 이동 (모두 한 번에, 회피 · 가속 없음)
Assets/Scripts/Data/NavGridConfig.cs        설정 (칸 크기 · 반지름 · 높이 띠 · 붙이기 반경)
Assets/Scripts/Data/NavBenchmarkConfig.cs   측정 설정
Assets/Scripts/Site/SiteNavGrid.cs          어댑터: SiteGrid 열린 칸 + Site 아래 충돌체 → NavGrid
Assets/Scripts/Debugging/NavBenchmark.cs    측정 도구 (단계 진행 · 기록 · 결과 표)
Assets/Scripts/Editor/NavBenchmarkMenu.cs   메뉴 `APC > Test > Nav Benchmark` → Play → 도구 붙이기
Assets/Data/NavGridConfig.asset · NavBenchmarkConfig.asset
```

- 코어 규칙: `APC.Site` · `APC.Staff` 같은 게임 코드를 참조하지 않는다. 장애물은 `NavBox` 목록으로 받는다 (충돌체에서 뽑든, 레일이 직접 등록하든).
- 측정 설정은 `GameDatabase`에 넣지 않는다 (측정용이라 게임 DB · Tycoon 복사본을 건드리지 않음). 메뉴가 에셋 경로로 읽어 넘긴다. 알파에서 게임에 넣을 때 `NavGridConfig`를 `GameDatabase`에 연결한다.

### 5.3 굽기

**칠하기**: 방 영역 안 장애물 `NavBox`마다 반지름(0.5 = 지금 NavMesh 굽기와 같게)만큼 키운 상자 안에 중심이 든 칸을 막는다. 닫힌 방의 칸은 전부 막힘.
**어댑터의 장애물 고르기**: `Physics.OverlapBox`(그 영역) → Site 아래 · 트리거 아님 · 높이 띠 0.3~2.0m에 걸친 충돌체. 바닥(높이 0.3 아래)은 빠진다. 지금 TycoonTest에선 선반 · 랙 · 사무실 가구 · 손수레 등 36개 + Play 중 선반.

| 범위 | 하는 일 |
|---|---|
| 전체 | 모든 방 칠하기 → 모든 문 → 모든 문 지도 |
| 방별 | 그 방 칠하기 → 그 방 네 변의 문 → 그 방 문 지도 + 공유 변의 문이 바뀐 이웃 방의 문 지도 |
| 타일별 | 물체가 걸친 2m 타일만 칠하기 → 칸이 실제로 바뀌었으면 그 방 문 지도 (변 타일이면 그 변의 문 · 이웃도) |

**문 지도**: 문마다 방 안 다익스트라 한 번 → 400칸 각각의 거리(ushort) · 문 쪽 다음 방향(byte). 방 안 문↔문 간선 비용 = 이 값. 메모리 약 64방 × 문 8 × 400 × 3바이트 ≈ 0.6MB.
**해금** = 방 열기: 방별(그 방 + 이웃) vs 전체.

### 5.4 길찾기

1. 출발 · 도착 칸을 가까운 걸을 수 있는 칸에 붙인다 (반경 2m, 못 붙이면 실패).
2. 같은 방이면 방 안 A*. 닿으면 끝.
3. 아니면 문 그래프 A*: 출발 → 출발 방 문들(비용 = 문 지도 값 조회), 문↔문(방 안 · 변 건너기), 도착 방 문들 → 도착. 휴리스틱 = 직선 거리.
4. 칸 길 = 문 지도의 방향을 따라 이어 붙임 (추가 탐색 없음).
5. 직선 펴기: 맵 격자에서 시야 검사로 꺾인 점만 남긴다 → 웨이포인트.

### 5.5 이동 (멍청해도 됨)

- `NavCrowd` 하나가 모든 알바를 한 `Update`에서 움직인다 (알바마다 `Update`를 두지 않음 — CPU 목적).
- 웨이포인트를 일정 속도로 따라가고 방향만 돌린다. 회피 · 가속 없음 (지금 NavMesh도 회피 끔).
- 다시 굽은 방을 지나는 길을 가진 알바만 다시 길을 찾는다. 길찾기는 프레임당 최대 N개 `임시`(줄 세움).

### 5.6 측정 도구 (`NavBenchmark`)

메뉴 `APC > Test > Nav Benchmark` → TycoonTest Play → 자동 진행 → `Logs/NavBench/<시각>/`에 결과 표(`result.md`) · 단계별 Profiler 기록(`*.raw`, Profiler 창에서 Load).

| 단계 | 내용 |
|---|---|
| 0. 보정 (선택) | 실제 알바 100명을 뽑아 60초 → 초당 길 요청 수(`StaffWorker.PathRequests`) · 실제 알바의 NavMesh 마커 기록 → 지움 |
| 1. 기준 | 측정 알바 0명 |
| 2. NavMesh 100명 | `NavMeshAgent`(알바 프리팹과 같은 설정) |
| 3. A* 100명 | `NavCrowd` + 방 2층 A* |
| 4. 길 1개 | 같은 무작위 출발 · 도착 1000쌍: `NavMesh.CalculatePath` · 방 2층 A* · 한 장 격자 A* (+ 자기 검사) |
| 5. 해금 | NavMesh `BuildNavMesh`(지금) · `UpdateNavMesh` 비동기(참고) · A* 전체 · 방별 |
| 6. 레일 1 · 10개 | NavMesh carving · NavMesh 전체 굽기 · A* 전체 · 방별 · 타일별 (+ 다시 길 찾은 알바 수) |

- **공평하게**: 2 · 3단계 알바는 같은 캡슐 모양 · 같은 속도(`StaffRules` 기본 속도) · 같은 시드의 목적지 순서 · 같은 시작 자리. 목적지 = 실제 서는 위치(`WorkSlot`, Play 중 선반 것 포함), 미리 한 번씩 NavMesh/격자에 붙여 둔다.
- **길 요청 빈도**: 알바마다 `100 ÷ (0단계에서 잰 초당 길 요청 수)`초마다 새 목적지를 받는다 (시작 시점은 무작위로 흩음). 먼저 도착하면 서서 기다린다. 0단계를 건너뛰면 설정값(4초 `임시`).
- **0단계 직무 나눔**: TycoonTest 비율(하차 20 · 보관 30 · 상차 20 · 지게차 8)을 100명으로 → 26 · 38 · 26 · 10. 끝나면 바로 지운다(걸어 나가기 없음).
- **해금 흉내**: TycoonTest는 다 열려 있으므로, 플레이어와 먼 방 하나를 닫았다가(NavMesh = 그 방 바닥 충돌체 끄기, A* = 방 닫기) 여는 비용을 잰다.
- **레일 자리**: 열린 방 안에서 기존 장애물 · 서는 위치와 겹치지 않는 자리를 시드로 고른다(20번 시도). 레일 10개 = **서로 다른 방 10개**에 하나씩 (방별 굽기에 가장 불리한 경우). NavMesh carving 시험용 레일은 선반처럼 `NavMeshObstacle`(carve) + 굽기 제외, 전체 굽기 시험용은 일반 충돌체.
- **carving · 비동기 비용**: 바꾼 뒤 30프레임 동안 NavMesh 마커 합 − 기준 × 30.
- **기록 값**: `PlayerLoop` ms/프레임(에디터 몫 제외, 중앙 · p95 · 최대), NavMesh 쪽 Unity 마커(실행 중 이름에 `AIUpdate` · `NavMesh` · `Crowd`가 든 것을 찾아 기록), A* 쪽 직접 단 마커 `Nav.Path` · `Nav.Move` · `Nav.Bake`, 두 쪽 공통 `Bench.Driver`, GC 할당/프레임, 굽기 ms(스톱워치), 메모리(A* 바이트, NavMesh 삼각형 수).
- 각 단계 예열 5초 · 측정 20초 · 3회 반복, 중앙값 `임시`.
- 비동기 · carving처럼 여러 프레임에 걸치는 것은 끝날 때까지 프레임 마커 합 − 기준.

### 5.7 자기 검사 (테스트 대신)

4단계에서 1000쌍마다: ① 한 장 격자 A*가 길을 찾으면 방 2층 A*도 찾는다 ② 방 2층 길 길이 ≤ 한 장 격자 × 1.4 `임시` (구현 중 1.3 → 1.4: 문이 변 가운데 하나라 대각선 길은 두 변 가운데를 거침, 자기 검사 최대 1.33 · 평균 1.02) ③ 웨이포인트 사이 직선이 막힌 칸을 지나지 않는다. 어기면 결과 표 맨 위에 실패로 적고 개수를 센다.

## 7. 정한 것 · 남긴 것

**사용자가 정함**: 측정 전용 알바로 비교 · 방 단위 2층 A* · 방 = 해금 단위 · 알바는 멍청해도 됨 · CPU 최적화가 목적 · 알파로 옮길 시스템.

**내가 정함 (고쳐도 됨)**: 격자 0.5m · 장애물 키우기 0.5m(지금 NavMesh와 같게) · 레일 = 6m × 1m × 높이 1m 상자(방 안 무작위 자리, 0° · 90°) · 문은 이어진 구간 가운데 하나 · 측정 20초 × 3회 · 에디터 측정만 · 결과는 `Logs/`(git 제외) · `UpdateNavMesh` 비동기 줄은 참고로 추가.

**구현하며 정할 것**: NavMesh 내부 마커 정확한 이름(실행 중 찾음), 프레임당 길찾기 상한 값, 직선 펴기의 시야 검사 방식.
